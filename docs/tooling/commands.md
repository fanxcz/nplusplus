# Tooling Commands

This reference documents the CLI workflow in the current N++ 1.0.0 source tree. Command options can vary by installed build; use `npp --help` and `npp doctor` to verify the local compiler and toolchain. Unsupported options produce an error.

## Interactive terminal

Run `npp` with no arguments or use `npp repl` to enter the interactive shell.
Each expression is compiled and evaluated by N++; `let`/`const` bindings and simple
assignments remain available in subsequent entries. An assignment to a name that has not been declared yet (for example `answer = 42`) is automatically treated as `let mut answer = 42`, so the shell accepts Python-style bindings. The shell accepts N++ syntax, not
Python syntax. Use `:help`, `:vars`, `:history`, `:history-clear`, `:clear`, or `:quit` inside the shell.

Submitted input is persisted between launches (the most recent 500 entries). On Linux/macOS
it defaults to `~/.npp_repl_history`; on Windows it defaults to `%APPDATA%\\N++\\repl_history.txt`.
Set `NPP_HISTORY_FILE` to choose a different file, for example for an isolated project or test.

```text
npp> 2 + 2
4
npp> let mut answer = 21
npp> answer * 2
42
```

## Project workflow

| Command | Purpose |
|---|---|
| `npp new <project> [--template NAME]` | Create a project in a new directory |
| `npp init [--template NAME]` | Initialize the current directory |
| `npp info` | Print the current project's manifest settings |
| `npp assets` | List files in known asset and scene directories |
| `npp clean` | Remove the project's `build/` directory |
| `npp doctor [--json]` | Report runtime, standard library, template and compiler availability |
| `npp self-test` | Compile and run a tiny program, preferring the built-in backend where supported |
| `npp editor [--gui]` | Generate VS Code workspace files, or run the built-in editor with `--gui` |

Supported project templates: `cli`, `app`, `game`, `3d`, `paint`, `server`, and `library`.

## Build and run

```bash
# Create, build, and run a project
npp new HelloNpp --template cli
cd HelloNpp
npp check
npp build --release
npp run --release

# Compile one source file
npp build src/main.npp -o hello --backend auto

# Ask which backend will be selected
npp explain-backend src/main.npp
npp explain-backend src/main.npp --target x86_64-linux

# Print supported target names
npp targets
```

The built-in machine-code backend avoids external compiler tools for its supported x86-64 Windows/Linux subset. The LLVM fallback is required for programs outside that subset and for targets supported through the configured Clang toolchain. Listing a target does not mean the built-in backend can emit it.

## Windows console output

When you run `npp run file.npp` from an already-open terminal, the output remains in that terminal. To run a source file from File Explorer, use the N++ context-menu action **Run with N++**; the installed launcher waits for Enter after the program ends so you can read its output. The standalone `Run-NAME.bat` generated by `npp build file.npp` does the same for a compiled `.exe`.

Double-clicking a console `.exe` directly is normal Windows behavior: the console window can close as soon as the process exits. Open the accompanying `Run-NAME.bat` instead when you need the final output to stay visible. The compiled `.exe` itself is not forced to pause, so command-line tools remain usable from scripts and other terminals.

## Windows graphics runtime DLLs

Windows builds that use the graphics/audio runtime load SDL2 dynamically. When the installed N++ runtime contains `SDL2.dll`, `SDL2_image.dll`, `SDL2_mixer.dll` and `SDL2_ttf.dll`, `npp build` copies them next to the output executable after a successful build. That makes the `.exe` launchable by double-click and keeps it independent of the shell `PATH`. Copies are skipped when no installed SDL runtime is found, which is the normal case on Linux/macOS builds and on machines that only use the console subset.

Supported build flags:

- `npp build [file.npp] [-o OUTPUT] [--target TRIPLE] [--backend auto|native|llvm] [--emit-ir] [--release]`
- `npp run [file.npp] [--target TRIPLE] [--backend auto|native|llvm] [--release]`
- `npp export [--target TRIPLE] [--backend auto|native|llvm] [-o OUTPUT]`

## Code quality

```bash
# Format the current project entry (or one file)
npp fmt
npp fmt src/main.npp

# Check without changing the file; exits nonzero if changes are needed
npp fmt --check src/main.npp

# Parse and run semantic checks
npp check src/main.npp
npp lint src/main.npp

# Generate API documentation from the project's entry file
npp doc
```

The formatter's `--check` mode never writes to the file. The formatter is deliberately modest; it is not yet a full syntax-aware pretty-printer. `npp fmt --all` formats `.npp` files in the project recursively, while `npp fmt --check --all` checks every discovered source without modifying it. Both skip `.git`, `.vscode`, `build`, `dist`, `vendor`, `node_modules`, `CMakeFiles`, `target`, and `.cache`. `lint` performs the current line-level checks and semantic analysis; it does not accept a configurable rule set or JSON output option.

## Testing and profiling

```bash
# Project test programs are read from tests/programs/
npp test

# Compile and run a self-contained built-in-backend check
npp self-test

# Run a source program repeatedly (default: five runs)
npp bench src/main.npp --runs 10
```

`npp test` builds and runs each `.npp` file beneath the project's `tests/programs/` directory. It reports no tests when that directory is absent. For compiler development, use the repository's CMake/CTest suite as documented in [Building from Source](../development/building.md).

## Package commands

```bash
npp pkg init
npp pkg add ../my-library
npp pkg list
npp pkg remove my-library
npp pkg update
npp pkg build
npp pkg publish
```

The current package manager supports local vendoring and creation of a local `.nxpkg` archive. `publish` does not upload to a hosted package registry. `npp pkg verify` validates local package checksums and checks that manifest dependencies, lockfile entries, versions, and paths under `vendor/` agree.

## Language server

Run `npp lsp` from an editor configured to launch the language server over standard input/output. The server provides diagnostics, completion, signature help, hover, go-to-definition, references, rename, whole-document and range formatting, quick fixes, a current-file Outline (`textDocument/documentSymbol`), and workspace-wide declaration search (`workspace/symbol`). Workspace files are cached and indexed for supported declarations, including unopened `.npp` files; workspace symbol search is capped at 500 results per request. Resolution is still lexical rather than a full type-aware semantic model: struct fields, enum variants, import aliases, and inferred types have known limitations.

## Diagnostics

```bash
npp doctor
npp doctor --json
```

The JSON form is intended for scripts. It emits booleans describing detected compiler, runtime, standard library, templates, and project availability. A missing LLVM compiler is not by itself fatal because supported source programs can use the built-in backend.

## General

```bash
npp --help
npp --version
```

See the [N++ Roadmap](../development/roadmap.md) for planned improvements and completion criteria.


REPL history persists between launches (up to 500 entries); `:history-clear` removes saved entries too. In an interactive terminal, Tab completes built-ins, keywords, current bindings, and declared functions/types; Up/Down recall history; Left/Right and Home/End move the cursor; Backspace/Delete edit the line; Ctrl+A/Ctrl+E jump to the start/end; Ctrl+U clears the text before the cursor; Ctrl+K clears to the end; and Ctrl+C cancels the current line. When standard input is redirected or piped, the REPL uses ordinary line-based input so scripts and automated tests remain compatible.


State is rebuilt from saved declarations and statements for each entry. Pure `if`, `while`, `for`, and `match` blocks that only use local expressions and assignments are retained so their binding changes persist. Blocks containing function calls or unsupported operations run once but are not replayed; the shell prints a note because mutations inside those blocks cannot currently be retained.


## LSP signature help

The language server provides function signatures while the cursor is inside a call. It reports parameter names and types for user-defined functions across the current workspace, and type-based parameter hints for built-ins whose signatures are defined by the runtime. Nested parentheses, array expressions, and struct literals do not incorrectly increase the outer call's active parameter.
